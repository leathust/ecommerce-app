Ràng buộc database bảo vệ điều gì?

  • UNIQUE: không trùng email, SKU hoặc cặp cart_id/product_id.
  • Foreign key: không tham chiếu ID không tồn tại; kiểu foreignId phù hợp với id unsigned của Laravel.
  • CASCADE: xóa cha kéo theo con, ví dụ ảnh khi sản phẩm bị xóa.
  • SET NULL: giữ bản ghi con và bỏ liên kết, ví dụ product_id trong order_items.
  • RESTRICT: từ chối xóa cha khi còn bản ghi tham chiếu.
  • decimal(18,2): lưu số tiền chính xác theo hai chữ số thập phân; tránh float cho tiền.

php artisan migrate

# Chỉ chạy migration chưa áp dụng.
# migrate:fresh xóa bảng để dựng lại: không dùng với dữ liệu cần giữ.

Bảng users giữ password, remember_token, email_verified_at chuẩn Laravel. password chứa hash, tương ứng ý nghĩa password_hash trong sơ đồ. Không thêm cột mật khẩu thứ hai.

04 · Model

Eloquent nối object PHP với các bảng

public function roles(): BelongsToMany
{
    return $this->belongsToMany(Role::class, 'user_roles');
}

$user->roles;                         // Lấy collection roles (lazy load)
$user->roles()->where('name', 'admin')->exists(); // Truy vấn tồn tại
$user->roles()->attach($roleId);       // Thêm liên kết pivot
$role->permissions()->sync($ids);      // Thay tập liên kết bằng danh sách mới

hasMany diễn tả một user có nhiều orders/carts; belongsTo là chiều ngược lại; belongsToMany cần bảng trung gian. Hai bảng pivot quyền không có model riêng vì quan hệ đã quản lý việc đọc/ghi chúng.

fillable, hidden, casts và timestamps khác nhau ra sao?
  • $fillable liệt kê cột cho phép mass assignment khi gọi create/update bằng array. Nó không thay thế validation hay kiểm tra quyền.
  • $hidden giấu password/remember_token khi serialize model, không ngăn truy vấn cột.
  • $casts chuyển đổi boolean, decimal, datetime. Dự án có một hàm casts() trong User: với Laravel 10 cần rà tương thích phiên bản cụ thể; không nên mặc định hàm này bảo đảm hash mật khẩu. Seeder hiện hash rõ ràng bằng Hash::make.
  • Model mặc định tự ghi created_at/updated_at. Các bảng không có đủ hai cột dùng $timestamps=false hoặc hằng CREATED_AT/UPDATED_AT=null.

Scope và accessor trong Contact

    ->status($filters['status'] ?? null)
    ->reason($filters['reason'] ?? null)
    ->latest()

search() gom các điều kiện OR trong một closure: (first_name LIKE ... OR email LIKE ...). Sau đó AND với status/reason. Nếu không nhóm OR, điều kiện lọc có thể bị sai logic. Query builder bind giá trị giúp tránh SQL injection; ký tự % và _ trong LIKE vẫn có ý nghĩa wildcard.

Dự án đang dùng truy vấn exists() trực tiếp cho quyền. Dễ hiểu, cập nhật quyền có hiệu lực nhanh nhưng nhiều @can có thể tạo nhiều query. Eager loading hoặc cache quyền là hướng tối ưu sau; khi cache cần có cơ chế vô hiệu hóa khi đổi quyền.

    ['email' => config('admin.email')],
    ['password' => Hash::make(config('admin.password')), /* ... */]

updateOrCreate tìm theo khóa đầu tiên, cập nhật nếu có hoặc tạo mới. sync thay toàn bộ tập permission của role; syncWithoutDetaching thêm role mà giữ các role đã có. Transaction đảm bảo các thao tác DB trong khối cùng thành công hoặc cùng rollback.

Idempotent ở đây nghĩa là không sinh dữ liệu trùng, không có nghĩa “không thay dữ liệu cũ”. Seed lại role sẽ đặt ma trận quyền về định nghĩa trong seeder. Seed lại admin sẽ đặt password/status/username theo ADMIN_* hiện tại.

.env → config/admin.php → config('admin.password'): biến môi trường được đọc qua config, phù hợp cơ chế config cache. Không ghi mật khẩu vào source hay tài liệu.

06 · Authentication

Đăng nhập là xác thực danh tính, sau đó mới xét quyền admin

AdminLoginRequest.php → AdminAuthController.php → User.php

  1. GET /admin: guest middleware và controller trả form login.
  2. POST /admin/login: web middleware đọc session và kiểm tra CSRF; FormRequest validate email/password/remember.
  3. Limiter: khóa theo email viết thường + IP; đủ 5 thất bại thì tạm từ chối 60 giây.
  4. Auth::attempt: dùng guard web/session và provider users, tra email và kiểm tra mật khẩu với hash.
  5. Kiểm tra active/admin: user bị blocked/inactive hoặc thiếu role quản trị bị logout ngay, session bị hủy và bộ đếm thất bại tăng.
  6. Thành công: xóa bộ đếm, regenerate session, redirect tới intended URL hoặc dashboard.
if (! Auth::attempt($request->only('email', 'password'),
        $request->boolean('remember'))) {
    $request->recordFailedAttempt();
    $this->throwAuthenticationException();
}

// Kiểm tra user->isActive() và user->isAdmin() ở đây.
$request->clearRateLimit();
$request->session()->regenerate();
return redirect()->intended(route('admin.dashboard'));

Cookie & session

Cookie giúp trình duyệt liên kết các request với session. Laravel lưu danh tính đăng nhập trong session; password không được gửi lại trên từng request dashboard.

Regenerate

Đổi session ID sau đăng nhập để chống session fixation. Logout gọi invalidate rồi regenerateToken để bỏ phiên và tạo CSRF token mới.

Remember me

Cookie ghi nhớ và remember_token cho phép phục hồi đăng nhập. Middleware active vẫn cần chạy trên request để chặn tài khoản bị khóa.

Tại sao mọi lỗi đăng nhập dùng cùng một thông báo?

Để không tiết lộ email có tồn tại hay không, user có role gì hoặc tài khoản đang bị khóa. Dữ liệu nhập sai định dạng vẫn có validation message riêng. Form không bao giờ điền lại password bằng old().

Frontend dùng @csrf, old('email'), @error. Checkbox remember có value="1" để hợp rule boolean. Nút loading chỉ cải thiện UX; bảo mật vẫn nằm ở backend.

07 · Authorization

Từ role đến quyền thực hiện hành động

usersAi?
↔
user_rolesuser_id + role_id
↔
rolesNhóm nhiệm vụ
↔
role_permissionsrole_id + permission_id
↔
permissionsĐược làm gì?
public function hasPermission(string $permission): bool
{
    if ($this->isSuperAdmin()) return true;

    return $this->roles()
        ->whereHas('permissions', fn (Builder $q) =>
            $q->where('permissions.name', $permission))
        ->exists();
}

Chỉ cần một role cấp quyền là user có quyền đó. Không có bảng permission trực tiếp cho user, không có “deny” override. hasAnyPermission là OR. User::permission(...) lọc liên kết thật trong DB, không tự bao gồm super_admin theo cơ chế bypass; khác với helper kiểm tra quyền.

Ba tầng sử dụng cùng RBAC

TầngCodeTác dụng

// AuthServiceProvider::boot()
Gate::before(function (User $user, string $ability): ?bool {
    return $user->hasPermission($ability) ? true : null;
});

true cho phép; null để Laravel kiểm tra Gate/Policy tiếp theo. Hiện không có Gate/Policy khác cho các ability module nên không có quyền sẽ bị từ chối. Bypass của super_admin nằm trong model và vì thế có hiệu lực cả middleware lẫn Gate.

Mô phỏng pipeline quyền

Mô phỏng ma trận seed mặc định để học, không truy cập database và không thay đổi quyền thật.

Thứ tự quan trọng: auth → active → admin → permission. Super admin vẫn bị chặn nếu account inactive. Một role mới dù có permission cũng chưa vào được admin nếu chưa thuộc Role::ADMIN_ROLES.

Vì sao trước đây modal bị màn đen che?

Modal nằm trong container nội dung có thể bị stacking context của template giữ ở dưới backdrop. Tăng z-index của con không luôn thoát được stacking context của cha. Dự án dùng @push('modals') ở view và @stack('modals') trong layout sau page-wrapper để modal và backdrop ở cấp body phù hợp.

JavaScript nghe show.bs.modal, lấy event.relatedTarget để biết nút nào được bấm; cập nhật form.action và textContent. Khi gửi thì disable nút. Validation hoặc transport lỗi giữ old input để thử lại. Các data attributes không phải ranh giới bảo mật.

Mail hiện gửi đồng bộ. SMTP lỗi được bắt qua TransportExceptionInterface và báo lỗi, chưa có retry queue, lịch sử phản hồi hoặc cơ chế chống gửi trùng tuyệt đối. Gửi thành công nghĩa là mail transport chấp nhận xử lý, chưa chứng minh khách đã nhận/đọc. Reply không tự thay status contact.

13 · Bài tập mở rộng

Công thức thêm một module mới

  1. Dữ liệu: xác định bảng/cột, nullability, FK, index; tạo migration bổ sung cho DB đã chạy.
  2. Model: fillable theo nhu cầu, quan hệ và query scope tái sử dụng.
  3. Quyền: định nghĩa module.view/create/update/delete trong seeder, gán role phù hợp.
  4. Request: whitelist dữ liệu, validation và authorize cho từng hành động.
  5. Route: đặt tên nhất quán, method đúng và middleware auth/active/admin/permission.
  6. Controller: điều phối query/action, trả view hay redirect; transaction khi nhiều thao tác DB cần đồng bộ.
  7. View: layout chung, CSRF, errors, old input, escape và @can.
  8. Test: happy path, validation, quyền thiếu, dữ liệu không tồn tại, lỗi external service.

Thử thiết kế lịch sử reply

Hướng mở rộng: bảng contact_replies có contact_id, admin_user_id, subject, body, delivery_status, sent_at. Không đánh dấu sent trước khi transport chấp nhận. Nếu gửi qua queue, cần xử lý failed jobs, retry và nguy cơ gửi trùng. Đây là bài tập thiết kế; code hiện tại chưa có bảng này.

Tự giải thích lại một chức năng bằng 6 câu

17 · Apache & .htaccess trong project

URL sạch được tạo trước khi Laravel nhận request

.htaccess là cấu hình Apache theo thư mục. Nó không phải PHP và không phải Laravel middleware. Apache có thể trả file tĩnh, redirect hoặc từ chối truy cập trước khi controller chạy. Các chỉ thị chịu ảnh hưởng của cấu hình server và cách Apache hợp nhất cấu hình thư mục; không nên hiểu ba file bên dưới như ba hàm PHP luôn chạy tuần tự.

Gốc project

ecommerce-app/.htaccess

Chặn các đường dẫn source phổ biến, thêm header và ánh xạ URL vào public.

Front controller

Canonical URL, giữ Authorization và chuyển request không khớp file/thư mục vào index.php.

Tắt directory listing và chặn các đuôi script server đã liệt kê trong assets.

2. Đọc cú pháp RewriteRule và RewriteCond

RewriteEngine On
RewriteCond TEST_STRING CONDITION [FLAGS]
RewriteRule PATTERN SUBSTITUTION [FLAGS]

Trong .htaccess, pattern thường khớp phần đường dẫn tương đối với thư mục chứa file và không có dấu slash đầu. Rule ở gốc project thấy admin/contacts; rule trong public thấy đường dẫn tương đối với public. Query string không thuộc chuỗi path mà RewriteRule khớp.

Ký hiệu/flagĐọc như thế nào trong code
^, $, ^$Đầu chuỗi, cuối chuỗi, chuỗi rỗng tương ứng trang gốc thư mục
(.+), (.*), $1Bắt ít nhất một/bất kỳ số ký tự và dùng nhóm thứ nhất từ RewriteRule làm đích

[L]Dừng lượt xử lý rules hiện tại; rewrite thư mục có thể tạo lượt xử lý mới. Không đồng nghĩa kết thúc toàn bộ request

3. Các nhóm rule tại gốc project

Options -MultiViews -Indexes

RewriteRule ^storage(?:/(.*))?$ public/storage/$1 [L,NE]
RewriteRule ^(?:app|bootstrap|config|database|docs|resources|routes|storage|tests|vendor)(?:/|$) - [F,L,NC]

RewriteRule ^public(?:/|$) - [L]
RewriteRule ^$ public/ [L]
RewriteRule ^(.+)$ public/$1 [L]

Trong file thật, rule ^storage ánh xạ sang public/storage phải đứng trước rule chặn source có chứa storage. Đích là Junction public của Laravel, không phải private storage/ tại gốc project. Nếu đảo thứ tự, ảnh upload tồn tại trên disk nhưng URL sạch sẽ bị Apache trả 403.

  • -Indexes: không liệt kê nội dung thư mục khi không có index. Không ngăn việc tải một file cụ thể nếu file đó được cho phép.
  • -MultiViews: tránh cơ chế content negotiation tự chọn file gần tên, gây xung đột router/rewrite.
  • Danh sách thư mục dùng (?:/|$) để chặn đúng thư mục hoặc phần con; tránh nhầm một tên chỉ có cùng tiền tố.
  • Rule public storage chỉ mở nội dung nằm dưới disk storage/app/public thông qua public/storage; private logs/cache không được ánh xạ.
  • Rule ^public giúp không tiếp tục gắn thêm public ở lượt xử lý đường dẫn đã vào public.
  • Trang gốc được đưa vào public/, các đường dẫn còn lại được đưa vào public/$1.
Chặn file nhạy cảm bằng FilesMatch 
<FilesMatch "^\.">
    Require all denied
</FilesMatch>

<FilesMatch "(?i)\.(?:bak|conf|dist|env|ini|log|sql|sqlite|yml|yaml)$">
    Require all denied
</FilesMatch>

FilesMatch xét tên file theo regex; ^\. nhắm tên bắt đầu bằng dấu chấm, còn (?i) bật khớp không phân biệt hoa/thường. Các rule này kết hợp với rule đường dẫn để hạn chế tải .env, log và bản sao cấu hình. Chúng không phải danh sách cho phép tuyệt đối cho mọi file/thư mục có thể xuất hiện sau này.

4. Tại sao dùng THE_REQUEST để redirect /public?

# Trong public/.htaccess
RewriteCond %{THE_REQUEST} \s/+(.*/)?public(?:[/\s?]) [NC]
RewriteRule ^(.*)$ /ecommerce-app/$1 [R=301,L,NE]

THE_REQUEST chứa dòng HTTP gốc, ví dụ GET /ecommerce-app/public/shop HTTP/1.1. Rewrite nội bộ không sửa dòng gốc này. Vì vậy request browser có /public mới bị canonical redirect; đường dẫn được Apache tự rewrite vào public không bị redirect lặp lại về URL sạch.

Project có rule xử lý /public ở cả gốc và public/.htaccess; hành vi thực tế còn phụ thuộc xử lý thư mục của Apache. Rule public dùng prefix cố định /ecommerce-app/. Đổi tên thư mục hoặc chuyển domain root phải rà cả hai nơi, không chỉ sửa APP_URL.

5. Chuyển request vào index.php

RewriteCond %{REQUEST_FILENAME} !-d
RewriteCond %{REQUEST_FILENAME} !-f
RewriteRule ^ index.php [L]

REQUEST_FILENAME là đường dẫn filesystem mà Apache đang xử lý; !-d nghĩa là không phải thư mục, !-f là không phải file. Nếu assets tồn tại, Apache trả file; nếu /admin/contacts không tồn tại vật lý, index.php nhận request và Laravel tìm route. File asset bị thiếu có thể rơi vào Laravel và nhận 404 HTML thay vì CSS/JS.

Rule redirect trailing slash phía trên chỉ áp dụng khi đích không phải thư mục. Điều kiện URI bắt đường dẫn bỏ slash cuối và dùng %1 làm đích 301. Rule Authorization dùng [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}] để giữ header cho PHP; chức năng login admin hiện dựa trên session cookie, không dựa trên Bearer token.

7. Cầu nối với public/index.php và APP_URL

Apache chạy script vật lý public/index.php nhưng browser dùng URL không có public. Code project chuẩn hóa SCRIPT_NAME và PHP_SELF, bỏ đoạn /public/index.php ở trường hợp URL sạch, giúp Laravel xác định base URL thư mục con. Đây là tùy chỉnh riêng cho cách chạy local hiện tại.

APP_URL=http://localhost/ecommerce-app giúp tạo URL, đặc biệt trong CLI; không tự bật rewrite hay thay DocumentRoot. asset('assets/admin/css/app.css') vẫn trỏ URL assets sạch. Không di chuyển file CSS/JS ra gốc để bỏ /public.

9. Giới hạn của cách triển khai hiện tại

Root project vẫn ở trong vùng Apache có thể phục vụ, nên cần rule chặn và phải rà khi thêm thư mục/file mới. URL sạch /storage/* hiện chỉ được ánh xạ vào Junction public/storage; private source storage, logs và cache không được phục vụ. File HTML này nằm trong docs bị chặn qua HTTP; mở bằng file local để học.

DocumentRoot trỏ thẳng public giúp giảm phần source nằm trong web root. Khi chuyển cách triển khai, cần rà các redirect /public và đoạn chuẩn hóa base path riêng, không copy nguyên cấu hình local mà không kiểm tra. .htaccess không áp dụng cho Nginx hay PHP development server như Apache.

Ôn tập nhanh: hãy tự giải thích trước khi mở
  1. Vì sao [L] chưa chắc chấm dứt mọi rewrite? Nó dừng lượt hiện tại; ánh xạ nội bộ có thể làm Apache xử lý lại theo thư mục.
  2. Tại sao asset tồn tại không cần Laravel controller? Điều kiện !-f không đạt nên rule front controller không chạy.
  3. Vì sao chỉ đổi APP_URL chưa bỏ được /public? APP_URL là cấu hình ứng dụng; Apache mới ánh xạ URL vào filesystem.
  4. 403 từ Apache khác 403 middleware? Apache có thể từ chối trước Laravel; middleware từ chối sau khi request đã vào ứng dụng.

Tham khảo chính thức: Apache .htaccess và RewriteRule flags. Nội dung mô tả cấu hình project tại thời điểm viết, không tự thay đổi cấu hình server.
